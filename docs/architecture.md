# Architecture

Pseudoharness is a localhost desktop-style web application with a React/Vite/TypeScript UI and Node/TypeScript service. The service controls Codex app-server over stdio JSONL and AgentMem through its already configured MCP stdio transport. It does not modify global Codex settings, invent an AgentMem HTTP API, or use direct API keys.

## Scheduling and contracts

The app loads `policy/CODEX_DELEGATION_POLICY.md` and injects it into each orchestrator thread's developer instructions and every orchestrator turn. This is a portable app-owned adaptation of the user-supplied policy; the global Codex instruction file is not read at runtime. Each new user prompt after a pass ends is routed independently: the orchestrator returns one validated branch, either a direct answer permitted by policy or a complete delegation assignment. The app-server requires a JSON object at the structured-output schema root, so this response uses one strict object with nullable branch-exclusive fields and server-side validation that rejects mixed branches. A root-level `anyOf` schema was rejected by the live Codex runtime; the current contract was verified through live direct and delegated turns. Direct answers create no worker thread and do not fabricate a worker receipt; their durable AgentMem item is recorded as a direct orchestrator answer. Explicit requests to use Luna and consequential tasks must delegate. In-flight user changes are serialized into one revision of that pass.

## Pass history and orchestration context

Every completed prompt is a separate persisted pass in the same app task, with its own user-input IDs, phase, assignment, receipt, review, error, reasoning summaries, Codex thread/turn IDs, completion-deduplication IDs, and AgentMem work record. The UI renders those artifacts within their pass, so a new direct answer cannot inherit the prior pass's assignment or receipt panel. A new pass starts a fresh orchestrator thread and, if delegated, a fresh worker thread; one consolidated correction for that pass reuses its worker thread. An in-flight user update remains within that pass and is applied after the active turn is interrupted or serialized.

The new orchestrator thread receives the current request plus bounded, role-labeled prior user-visible conversation history. That history includes previous user requests and the assistant-visible direct answer or accepted orchestrator response, so follow-ups such as “double that result” remain meaningful. Earlier assignments, receipts, worker messages, tool events, and reasoning summaries are not replayed as current instructions or supplied as worker transcript. Historical user controls are explicitly context, not current instructions. Current explicit instructions such as “do not delegate” remain attached to the latest request and the configured orchestrator model ID comes from app settings. Thread events are accepted only for the current pass's thread; late completion, progress, approval, or reasoning-summary events from older passes are ignored. The scheduler wake rules remain unchanged.

State version 1 is migrated without deleting messages or work artifacts. Because the earlier format had task-wide fields and no message-to-assignment links, migrated assignment/receipt panels are marked legacy and unassociated rather than attributed to an arbitrary prompt. New prompts in a migrated task create an explicit pass and fresh Codex threads.

Delegated tasks have separate orchestrator and Luna threads. The complete schema-validated assignment must pass validation and write-root checks before the worker starts. Assignment scope has explicit read and write arrays; empty read scope is allowed for answer-only work, while empty write scope authorizes no filesystem writes. Non-empty write roots are validated inside the selected workspace before being passed to Codex. Luna is explicitly `gpt-6-luna` with high effort and is not replaced with another model. Completion is idempotent by turn ID. A correction is limited to one consolidated update and reuses the worker thread.

The only orchestrator wake causes are explicit user input, an explicit structured worker escalation, and a final receipt. Progress events and timers update the UI but cannot schedule inference. Worker transcripts and tool output are not passed to the orchestrator. Assignments, receipts, escalation, and review decisions are validated server-side; invalid results stop the workflow with an actionable error.

## Approval and sandbox

The composer exposes Codex approval presets, serialized to app-server's `approvalPolicy`: `on-request`, `untrusted`, or `never`. The app-server `sandboxPolicy` separately sets worker turns to `readOnly` when no write roots are authorized or `workspaceWrite` with validated roots and network access disabled when writes are authorized. Orchestrator turns are read-only. `never` suppresses prompts; it does not broaden sandbox access. No danger-full-access preset or custom approval editor is implemented.

When app-server sends a command/file-change or permission approval request, the service records it against the correct task and presents details in the UI. The user can accept, decline, or cancel; the service answers the original server request ID using the method's protocol response. Requests for unsupported methods are rejected and shown as actionable errors. The protocol is experimental and this request handling should be revalidated after CLI updates.

Read scope is still prompt/assignment guidance rather than an OS-level read restriction. The actual read/write boundary depends on the user's installed Codex sandbox and profile. Localhost binding and request-origin checks limit access to the local machine, but the service has no authentication system and must not be exposed to a network.

## Reasoning channels

The app keeps Codex's readable summaries and provider-emitted reasoning text in separate channels. Both `thread/start` and `thread/resume` request detailed summaries and set the per-thread `show_raw_agent_reasoning` config flag; `turn/start` does not accept this thread config. The app consumes `item/reasoning/summaryTextDelta` and section boundaries, and reconciles them with the completed item's `summary` array. It separately consumes `item/reasoning/textDelta` by `contentIndex` and reconciles it with string entries in the completed reasoning item's `content` array. Both channels are bounded and scoped to pass, role, thread, turn, and item; late events from another role or turn are ignored.

Each reasoning turn is rendered as the corresponding model's response row in the conversation timeline at its recorded start time. The row updates as deltas arrive, showing provider-emitted raw text when available and otherwise falling back to the readable summary. If neither channel emits text, it shows an honest waiting or unavailable message. Structured assignment/receipt/final-answer messages remain separate; the generic “Prepared a complete assignment.” status is hidden when that pass has a corresponding orchestrator response row. These response rows are derived UI only: reasoning data is never added to the normal conversation messages or passed into another model's prompt.

The raw-text flag asks Codex to surface raw reasoning when available; it cannot make an underlying model/provider emit content that it does not provide. The app stores only the readable text-delta and completed-item content strings it receives in local task state. It does not inspect or persist `rawResponseItem/completed` or encrypted raw-response content, and neither summaries nor raw text enter another model's prompt or trigger an inference turn. Provider/account/model availability therefore remains variable. The event and config behavior was checked against the installed app-server protocol and [official Codex app-server documentation](https://developers.openai.com/codex/app-server/) and [configuration reference](https://developers.openai.com/codex/config-reference/).

Assistant responses, worker receipt results, and readable summary text use safe CommonMark/GFM rendering. Raw HTML is not enabled; links use the renderer's safe URL handling and open in a protected new tab.

Scrollbars use a thin rounded dark thumb and track across scrollable desktop regions. Native arrow buttons are hidden where Chromium exposes scrollbar pseudo-elements; forced-colors mode restores system colors for accessibility.

## Persistence, recovery, and AgentMem

The app stores task IDs, pass IDs, thread/turn IDs, revisions, messages, and completion deduplication state in the operating system's local application-data directory. Active work is paused on restart and is never automatically replayed. Explicit user action attempts to resume the saved Codex thread; unavailable threads or active-writer conflicts remain paused for inspection. Cancellation is saved before a best-effort interrupt, and late events for cancelled tasks or superseded passes are ignored. A user update during work interrupts/serializes the existing turn before one consolidated update is scheduled.

Settings require a workspace root. An AgentMem project is optional; a blank ID explicitly disables retrieval, task creation, receipt saving, and retries for new tasks. Tasks pin the selected project ID at creation, so changing Settings does not attach or detach old work or leak old project context. Nonblank IDs must already be registered and match the selected root. With a selected project, the service retrieves scoped requirements, accepted lessons, and evidence before assignment. Durable work receipts and runtime thread state remain separate. AgentMem completion includes acceptance evidence and the current requirement revision; the AgentMem service decides whether the task is done and clears the lease. Incomplete results remain in progress and release ownership; blocked results are recorded as blocked then released; cancellation releases ownership. Adapter errors remain visible in app state rather than claiming persistence succeeded.

The details inspector separates live project settings for future tasks from the immutable root and AgentMem association recorded for the selected session. Saving Settings updates the live values and runtime verification state; it does not rewrite that session's task or pass history.

Session rename validates a trimmed, non-empty title up to 120 characters and updates the local app record without starting a model turn. Session deletion removes only that local app record and its saved conversation history. It is rejected while a turn is active or an AgentMem receipt is saving/leased. Codex threads and AgentMem records are not deleted, and deleting the selected app session clears the selection safely.

An AgentMem task-context response can omit mandatory project requirements when its metadata and evidence exceed the response budget, returning a `next_requirement_offset`. The adapter now follows those supported continuation offsets and combines the pages before building completion checks. If required pages cannot be fetched, it leaves the task incomplete, releases its lease, and reports the failure. An explicit retry action can reclaim an accepted app-owned work record and resubmit the saved receipt using a fresh idempotency key; AgentMem's current ownership/claim response is authoritative if a persisted local lease token is stale. A live AgentMem-only smoke verified `done`, empty owner, and `lease_until=0`; six accepted app-owned smoke records were retried and verified done/released. No model inference was used for these retries.

The accepted `20+2` screenshot showed AgentMem's “saved, task still open” state while completion was still being submitted. The underlying scoped work record was later verified done with its lease released, so this was a transient UI state rather than a wrong arithmetic answer or a reason to retry concurrently. Accepted passes now show “Saving AgentMem receipt…” until the save/completion call resolves; retry is offered only after an accepted record is still open and the app no longer holds its lease. A direct-answer record-creation failure is displayed with its error, without inventing a retryable work-task ID.

## Local security

The server binds to `127.0.0.1`, rejects non-loopback hosts and mismatched origins, uses a process-local mutation token, bounds JSON payloads, and starts app-server without constructing shell command strings from task content. Runtime state, environment files, dependencies, build output, and temporary QA files are ignored by Git. The application is intended for one local user and does not provide a network deployment model.

## Deferred work

The requested roadmap items are listed in [ROADMAP.md](../ROADMAP.md): editable custom approval policies, multimodal task input, and a user-facing worker-session viewer. Worker and orchestrator already run in separate Codex threads, but the app does not yet offer a Codex-style session switcher or transcript viewer. This release does not implement these deferred features.
