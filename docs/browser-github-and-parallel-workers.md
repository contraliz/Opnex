# Browser and local GitHub workspaces

## Peer workspaces and session ownership

Session, Browser, and Git tabs share the app's tab strip and horizontal pane groups. A Browser or Git action from the rail, an empty-session shortcut, or a workspace command opens/selects a peer tab in the focused pane; it leaves the session tab in that pane. Session tabs use the session name, Browser tabs use **Browser** with a globe icon, and Git tabs use **Git** with a branch icon. Tabs can be selected, moved, split, resized, and closed using the same workspace controls.

Each session tab renders its own conversation, composer, attachments, errors, approval controls, and compact Stop/Heads-up icon controls within its content. The user rejected the separate action bar; these controls have no full-width row background or divider and never appear in the tab strip. In a split layout, both selected session panes can remain active together. A Heads-up panel is anchored to its session tab and shows that task's status, route, current pass threads, cumulative all-pass token totals, recorded session settings, and current settings for new tasks. Switching sessions does not redirect another tab's Stop action, draft, or panel data.

Browser and Git tabs capture their originating task/root when they open. Browser annotations return to that captured session if it still exists, even if another session becomes selected in the app. Git stays bound to the captured task repository or settings-level root. These IDs are app workspace identity only; task routing remains session-scoped.

## Browser and annotations

Each app-level **Browser** tab owns one sandboxed Electron `WebContentsView` with no Node integration or remote-page preload. The native page has stable workspace identity across app-tab switches; the app strip supplies browser tabs and panes, so the Browser surface does not add a second redundant top-level tab strip. Its compact address bar supports navigation, reload, back/forward, keyboard-accessible common-address suggestions, and a **Commenting** mode modeled on Codex's browser chrome. A bare hostname is normalized to HTTPS; explicit HTTP remains available for local fixtures, and credential-bearing or non-HTTP(S) addresses are rejected. Browser content fills the selected pane, and the native view tracks the measured renderer rectangle in CSS/DIP coordinates, clipped to the BrowserWindow content bounds. The normal web app can display the browser controls, but native site rendering requires `npm run desktop`.

Website cookies and storage stay in Electron’s persistent local profile. On Windows this profile is stored under `%LOCALAPPDATA%\Pseudoharness\browser-profile`; on macOS and Linux it is under the app’s OS user-data directory. Temporary smoke runs use a separate disposable profile. Pseudoharness’s browser and annotation features do not export browser cookies, site storage, auth headers, or browser session files to its Node API, task state, AgentMem, Codex prompts, logs, or a remote service. A site still receives its own normal authenticated browser requests. Device backup, profile redirection, or folder-sync software configured outside Pseudoharness can affect files in those locations.

To annotate a page, turn on **Commenting** and click the page target. The app captures only the clicked element's bounded text, current text selection, page title, and a URL with credentials, query, and fragment removed. It redacts common token, bearer, password, API-key, and cookie-shaped text patterns as a second boundary. It does not capture a screenshot or read the rest of the page. While the form is open, Electron reduces that Browser tab's native surface to leave an interactive area for the React annotation form. Add a comment and choose **Add to message**; the annotation is appended to the captured originating session's composer draft and follows the normal user-message path for a new task or follow-up. A deleted originating task is reported instead of silently redirecting the annotation to a different session. Page-derived text is labeled untrusted reference data. A user comment remains the user's instruction. Pseudoharness does not promise that agents can see page pixels; they receive only the text included in the submitted message.

This is an application data-flow boundary, not a file-system access-control guarantee. Browser profile files remain on the same device under the current OS user; other local processes or agent commands that already have filesystem permission may be able to read files available to that user. Keep the configured Codex sandbox/approval policy and task file permissions in mind when using locally authenticated browser sessions.

Use **Clear local browser data** to clear website data from this device's Pseudoharness profile. A website may expire or revoke its own cookies; Pseudoharness does not extend them. Website sign-in and GitHub CLI sign-in use separate local stores.

## Native GitHub and local Git

The app-level **Git** workspace is a local React interface. It does not load `github.com` for repository metadata. It reads the captured task/settings repository with argument-array `git` calls and, when available, runs read-only `gh` commands for repository, pull-request, and issue metadata. The Git page includes **Sign in with GitHub**; it checks the local GitHub CLI and can start its web/device sign-in flow. The app displays the device code and verification address, which opens in a new Browser peer tab. The user completes authorization with GitHub; Pseudoharness does not ask for, type, or receive the user's GitHub password or token. `gh` keeps its credential in its configured local credential store; Pseudoharness returns only bounded auth status/account labels and selected repository metadata, never token contents. Network failure, missing Git/GitHub CLI, missing authentication, and folders outside a Git repository leave local status visible with a useful explanation. A fixture-only UI check exercised the device-code display; no real GitHub account authorization was performed during that verification.

The Overview, Branches, Worktrees, History, Pull requests, and Issues views show local branch and remote-ref names, all reported linked worktrees, and local commit relationships, with branch and history pagination. The graph draws every commit parent, including both sides of merges, and marks parents beyond the loaded/filtered range. It displays up to 100,000 branch refs and the newest 10,000 commits; the UI reports those limits instead of offering an impossible next page. Pull-request and issue tabs each show up to 20 open items. The native GitHub views are read-only: they do not push branches, create or edit pull requests, or change issues. Selecting a task’s stored GitHub repository or pull-request command opens this local metadata view. Links can be copied for opening elsewhere.

Local Git inspection is separate from optional `gh` metadata requests: missing credentials, network access, or a slow GitHub CLI call do not hold up local branches, worktrees, or history. GitHub commands run separately and return only the selected bounded metadata. Existing agent shell commands remain governed by the task’s configured runtime approval policy. The local Git/GitHub interface does not provide browser content or cookies to task messages. Agents’ broader local filesystem visibility still follows their configured execution sandbox and approval policy. Ordinary `gh` network requests and authenticated browser page requests remain local app features using their respective local credential stores.

Run `npm run desktop` for the Electron app. Run `npm run dev` for UI iteration; the browser page itself remains a desktop-only feature. `npm run desktop:interaction-smoke` runs an isolated Electron fixture with a harmless local page and repository, exercises target click through the unsent task draft, checks responsive sizing and reduced motion, and saves screenshots under `artifacts/browser-git-workspace/`: `electron-annotation.png`, `electron-annotation-target.png`, `electron-git-overview.png`, `electron-git-branches.png`, `electron-git-worktrees.png`, `electron-git-history.png`, and `electron-git-history-narrow.png`. GitHub CLI can be installed separately from [cli.github.com](https://cli.github.com/).

## Pass-specific Git change capture

The **Git changes recorded for this pass** panel in a run receipt reads the selected pass's persisted Codex `turn/diff/updated` events. Each event contains the latest cumulative unified diff for one thread and turn, so a later event replaces that turn's previous value; the UI keeps separate turns separate rather than adding their line counts into a misleading pass-wide net. Only a currently active writing role (simple implementation, orchestrator, or worker) on its task-owned thread and turn can update the current pass. Stale turns, foreign threads and completed passes cannot update it. The pass endpoint never runs `git status` or `git diff`; the separate workspace Git viewer remains a live workspace view and may include changes from other sources.

Older passes without saved events show that Codex did not report a tracked turn diff; their current workspace is not used to reconstruct history. Codex reports turn-level tracked diffs based on its tracked patch mutations rather than rereading the workspace filesystem, as described by [`turn_diff_tracker.rs` at Codex commit `398500106707f0a3217c7cf83edc2bf226cc342f`](https://github.com/openai/codex/blob/398500106707f0a3217c7cf83edc2bf226cc342f/codex-rs/core/src/turn_diff_tracker.rs) and the [app-server notification schema at the same commit](https://github.com/openai/codex/blob/398500106707f0a3217c7cf83edc2bf226cc342f/codex-rs/app-server-protocol/schema/json/ServerNotification.json). The capture is bounded to 16 turns, 96 KiB per turn, and 384 KiB per pass. A limit is labeled partial. Shell, generated, and other writes that do not appear in the Codex turn-diff event may be absent; therefore this view is an attributed Codex patch record, not an audit of every filesystem mutation or a combined net diff across all turns.

## Implementation references and public Codex research

### Public Codex embedding research

The selected GitHub connector was used to search the public `openai/codex` repository for `WebContentsView browser`, `BrowserView electron browser tab`, and `embedded browser open URL browser chrome`. Those searches returned no matching browser-embedding implementation. The public repository README describes the Codex CLI and does not document a desktop browser embedding surface, so this pass does not claim to reproduce an unpublished Codex desktop implementation. The Electron page host follows the public [`WebContentsView`](https://www.electronjs.org/docs/latest/api/web-contents-view) and [`View` bounds](https://www.electronjs.org/docs/latest/api/view) APIs. The in-app sign-in flow was checked against the [`gh auth login` manual](https://cli.github.com/manual/gh_auth_login), [GitHub CLI login source](https://github.com/cli/cli/blob/trunk/pkg/cmd/auth/login/login.go), and [device-flow source](https://github.com/cli/cli/blob/trunk/internal/authflow/flow.go); the Codex CLI repository [README](https://github.com/openai/codex/blob/main/README.md) was the scope reference for the connector search.

The same public Codex repository does document its desktop-thread deep-link shape in [`open_desktop_thread` in `history_ui.rs`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/tui/src/app/history_ui.rs), which constructs `codex://threads/{thread_id}`. Pseudoharness uses that exact-thread URI through a narrower local bridge: the renderer passes a bounded raw thread ID, Electron validates it and constructs the fixed-scheme URL before calling [`shell.openExternal`](https://www.electronjs.org/docs/latest/api/shell/). This follows Electron's [security guidance](https://www.electronjs.org/docs/latest/tutorial/security/) not to pass untrusted renderer-controlled URLs to external open handlers. This thread-opening source does not imply that the public Codex repository contains a browser-embedding implementation.

## Session pane groups and workspace animation

All three peer types—sessions, Browser, and Git—can be rearranged between independent horizontal pane groups by dragging a tab onto a pane or another tab. Dragging over the left or right half of a pane creates a new adjacent group; groups retain their own selected workspace. Session groups retain their drafts and pending attachments; Browser/Git retain their captured context and native identity. Closing the last tab in a group removes that group while preserving at least one new-session tab. The dividers resize adjacent groups, and the session explorer can collapse below its minimum width. The left rail and centered new-session actions open/select workspace peers in the focused pane.

Tab/content arrival, open/close, split/collapse, first submission and Heads-up disclosure use short CSS motion; `prefers-reduced-motion: reduce` disables those effects. Polling and streamed task updates do not restart tab-entry motion.
