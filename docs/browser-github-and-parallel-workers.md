# Browser, GitHub, and parallel work proposals

## Browser and GitHub access

The primary entry points are the **Browser** and **GitHub** workspace tabs beside Tasks. They use the same full workspace area as the task conversation. Drag either workspace tab onto Tasks to dock the workspace beside the active conversation. The workspace toolbar also has a keyboard-accessible **Dock beside chat** button, and its side view has **Open full workspace**. In the optional Electron shell, web pages are native Chromium `WebContentsView` surfaces. Moving Browser or GitHub between full view and the chat side pane changes only the view bounds and pane assignment; the same `WebContentsView` and persistent session remain alive. GitHub side view keeps its task repository, branch, diff, checks, and user-confirmed push/PR controls visible alongside chat. Browser page tabs can still be split within the full Browser workspace using per-tab controls and the adjacent drag target. Website cookies and storage use Electron's persistent `persist:pseudoharness-browser-v1` partition. Website expiry and sign-in policies still apply. Sites that issue only transient session cookies can require a new sign-in after app exit; the app does not rewrite those cookies to extend authentication. Use a site's own “remember me” option where available. `npm run desktop:smoke` verifies a website-issued persistent cookie across two app launches using a disposable local profile, without accessing an account. Use **Sign out of websites and clear browser data** to clear the partition. The ordinary Vite browser app continues to work and directs users to the desktop shell for native embeds.

Run `npm run desktop` from the source checkout (Node.js and Codex CLI prerequisites are the same as the regular app). This builds the app, launches Electron, and starts the local backend in the app-owned user-data folder. Run `npm run desktop:package` on the target operating system to create an unsigned package under `desktop-release/`: a ZIP containing the macOS app or a Windows NSIS installer. CI builds both packages and launches each packaged app in a disposable profile. No signing certificates are configured; signing/notarization is a release task. GitHub repository inspection and write actions use the `git` and `gh` executables from `PATH`; install GitHub CLI and run `gh auth login` before using them. `gh` credentials are managed by GitHub CLI's credential store. Browser website login is a separate persistent Electron session and does not sign in GitHub CLI. The implementation does not put either credential in task state or model prompts.

The GitHub workspace associates repository, branch, base branch, and created PR URL with the selected Pseudoharness task. It combines branch/repository status, a read-only live local diff, current PR/check information, and explicit **Push committed changes** and **Create pull request** actions. Push never commits uncommitted files. PR creation requires the selected head branch to already exist on `origin`. Newly started Luna worker threads also receive a bounded `pseudoharness.workspace` app-server tool during their execution stage. It can open a credential-free Browser URL, show the current task repository or PR, dock/undock the workspace, and return a small repository/PR/check summary. Opening/docking views requires the Electron desktop shell; `inspect_github` is also available in the portable app. Calls must match the active task, pass, worker thread, and execution stage. The tool cannot read page contents, obtain cookies/tokens, push, or create a PR. A resumed worker thread created before this tool was introduced retains its old tool catalog and must be restarted as a fresh task to receive it. Worker `git`/`gh` commands remain subject to their normal Codex sandbox, approval, network, and assignment scope; the worker receives no GitHub token or browser session through Pseudoharness. The app's direct push/PR buttons remain explicit user actions. No claim of universal superiority over other GitHub integrations is made; the implementation's intended efficiency improvement is the saved task-to-repository/branch/PR link and one view of local diff, checks, push, and PR state.

These embeds intentionally do not bypass website framing policy: remote pages run as separate, sandboxed WebContentsViews with no preload or Node integration. Only HTTP and HTTPS URLs are allowed, browser permissions are denied, and website credentials never enter the local app renderer. Browser session data is stored under Electron's OS-managed Pseudoharness user-data directory, not in the source checkout. The Electron shell is optional; normal `npm run dev`, `npm run start`, and portable npm packaging remain web-based.

## Entry point proposals

- **Delivered:** Full-area Browser and GitHub workspace tabs next to Tasks, plus a persistent side pane that keeps the task conversation visible.
- **Delivered:** Drag the Browser or GitHub workspace tab onto Tasks to dock it, with keyboard-accessible dock/undock controls. The same native browser page instance and login session survive movement.
- **Delivered:** Task-scoped Luna workspace actions for opening browser/repository/PR views and inspecting minimal GitHub status; remote writes remain user-confirmed or use the worker's existing approval boundary.
- **Delivered:** The two-page Browser split and accessible per-page main/side controls.
- **Future option:** A task-card “Open repository” action that switches to GitHub with the task's stored repository/branch/PR context.
- **Future option:** A command-palette action to open a repository, pull request, or browser URL in the chosen pane.

The first two are implemented. The latter two are proposals for a later task; they are not prerequisites for finding the current workspace tabs.

## One orchestrator coordinating parallel local implementation tasks

**Current verified behavior:** A hard task has one configured orchestrator and one Luna worker thread. A correction reuses that worker; the app has no parallel-worker scheduler or managed-worktree integration today. Current push/PR UI actions target the task's existing selected local working directory.

**Proposed model:** Keep Sol/Astra as the sole decision owner. It creates one task plan with independent work packages, explicit file/API ownership, dependencies, shared contracts, acceptance criteria, and separate authorized write roots. Start one Luna/high worker per independent package in a dedicated Git worktree with only that package's complete assignment and the minimal scoped project context. Keep the coordinator dormant after dispatch. Wake it only for a worker's explicit decision escalation, user input, or final receipt; ordinary progress remains visible but does not start a coordinating turn. Workers never merge, edit a shared checkout, expand another worker's scope, or message each other. The coordinator integrates completed branches, resolves conflicts, performs cross-package tests and review, and produces one consolidated task receipt.

Parallel work is a good fit only when contracts and file ownership are separable. Shared schema, lockfile, state-machine, or UI-shell changes should be assigned to one worker or serialized. Integration must verify the exact worktree base and changed file set before applying a result. Each worker's runtime should retain the app's isolated Codex configuration, per-assignment write roots, approval policy, network policy, and transcript exclusion; worktree isolation is not a substitute for those boundaries. GitHub CLI/browser auth should remain local and must not be copied into worker prompts or another worktree. A real implementation would need bounded worktree lifecycle/cleanup, cancellation and crash recovery, branch provenance, final-receipt validation, resource/rate-limit controls, conflict detection, and a policy for workers that share one signed-in account. Account quota, simultaneous Codex sessions, disk usage, tool contention, stale dependency assumptions, and integration conflicts can erase the speedup. Recommendation: prototype only after independent package boundaries and app-server capacity are measured, and retain serial execution as the default.

## Implementation references

- Electron keeps browser page contents separate from the app renderer through `WebContentsView`, with each view configured using sandboxing, context isolation, and no Node integration: [Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view), [persistent session partitions](https://www.electronjs.org/docs/latest/api/structures/web-preferences), and [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security/). The packaged backend runs in a Node-enabled utility process rather than reopening the app binary as Node: [Electron UtilityProcess](https://www.electronjs.org/docs/latest/api/utility-process).
- Desktop packaging uses the platform-native targets documented by [electron-builder](https://www.electron.build/docs/features/multi-platform-build/); CI builds the app on both matrix operating systems.
- GitHub CLI uses its own authentication flow and supports explicit repository, head/base, title, and body when opening a PR: [gh auth login](https://cli.github.com/manual/gh_auth_login) and [gh pr create](https://cli.github.com/manual/gh_pr_create).
- Worker workspace controls use Codex app-server's experimental `dynamicTools` and client-handled `item/tool/call` flow; the server validates each request against the active Pseudoharness task/pass/stage before changing UI state: [Codex app-server dynamic tool calls](https://developers.openai.com/codex/app-server/).
