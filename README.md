# Pseudoharness

Pseudoharness is a local Codex request-routing and delegation app with a headless execution kernel. Each request is classified by GPT-6 Luna at low effort with the Fast tier. Direct answers use a separate read-only Luna turn at high effort; bounded implementation uses Luna at xhigh; hard tasks use the configured Sol/Astra Codex orchestrator, then DeepSeek Harness for recruited execution workers and integration, with Codex reviewing the combined receipt. The app records each provider's selected model and requested effort; DeepSeek Harness does not report whether its requested native effort was effective. Explicit requests to consult the selected AgentMem project knowledge base use the project-scoped workflow. The app-owned policy is in [`policy/CODEX_DELEGATION_POLICY.md`](policy/CODEX_DELEGATION_POLICY.md). This independent project is not affiliated with OpenAI.

## Requirements

- Node.js 22.12 or newer and npm to run from source or use the portable npm package. The packaged Electron app includes its runtime. Use Node.js 22.22.2 for source checks; it satisfies the locked jsdom test environment's runtime requirements and is the version used in CI.
- For Codex-backed tasks, Codex CLI must be installed and signed in, with `codex app-server --stdio` available. Routing requires GPT-6 Luna low effort and the Fast (`priority`) service tier; direct answers require Luna high effort. The runtime must support the short-lived external-auth bridge, per-thread base/developer instructions, and empty `instructionSources` acknowledgement for new and resumed agent threads; otherwise those roles fail closed. Hard-task recruitment also requires the DeepSeek Harness desktop SDK and a signed-in provider account. The current native desktop SDK launch is verified on Windows; other operating systems require an explicitly configured, verified SDK launch. The signed-in accounts must have access to their selected models. The app window can still launch without either model runtime; unavailable work fails with an actionable provider error rather than silently switching providers.
- A workspace directory to choose in Settings.
- Optional: AgentMem available as an MCP stdio server in the same Codex environment. Settings can keep it disabled, select an existing project, or enable a per-folder KB that the execution agent registers through audited AgentMem tool calls.
- Optional: GitHub CLI (`gh`) for GitHub account and repository features. Local Git workspace data remains available without `gh`.

### macOS first run

In Terminal, check the existing Codex sign-in with `codex login status`, then run `npm ci --include=dev` and `npm run dev` from this checkout. Open <http://127.0.0.1:5173> and choose a workspace in Settings. No separate Mac app bundle is required; the app runs locally in your browser and stores its state under `~/Library/Application Support/Pseudoharness`. Use `npm run package` to build the portable npm tarball instead.

The model and effort selectors use the catalog returned by the Codex executable the app launches. If an expected model is marked unavailable or its effort selector is disabled, check `codex --version` and point the app at a newer runtime with `CODEX_EXECUTABLE=/path/to/codex npm run dev`. This override leaves the CLI on `PATH` unchanged.

### Optional Electron desktop shell

From a fresh clone, install the locked dependencies before the first launch:

```sh
git clone https://github.com/contraliz/pseudoharness.git
cd pseudoharness
npm ci --include=dev
npm run desktop
```

Use Node.js 22.12 or newer. `npm ci --include=dev` installs the project-local development tools used by the source build, including TypeScript, Vite, and Electron, even when `NODE_ENV=production` is set. Run it again after pulling a change to `package-lock.json`. Do not install TypeScript globally or omit development dependencies for a source build; if TypeScript or Vite is missing locally, the build stops with this install instruction before clearing existing build output.

The desktop shell starts the local execution kernel in the OS-managed Pseudoharness data directory and adds native Browser and local Git workspaces. Its system tray icon uses the app's P mark. Closing the session window leaves Pseudoharness available from the tray; **Open Pseudoharness** restores the existing window or creates a new client for the same kernel, and **Quit** safely shuts down only a kernel started by that shell. An independently attached kernel keeps running when its client quits. Session, Browser, and Git are peer tabs in the shared app workspace; opening Browser or Git keeps the session tab and can split or move among panes. Each session's compact Stop and Heads-up icon controls stay inside that session's content, without a separate action bar or tab-strip controls. Each Browser peer owns a persistent-profile native `WebContentsView` that fills its pane. Remote browser pages have no app preload, Node integration, or browser permissions. Site expiry and sign-in policies still apply; use a site's own “remember me” option if it offers one. Browser data can be cleared from Settings. Run `npm run desktop:package` on macOS or Windows to create a desktop build in `desktop-release/` (zip app on macOS, NSIS installer on Windows); these local builds are unsigned. The Windows installer requests administrator permission when opened and installs for all users; the installed Pseudoharness app itself runs as the signed-in user. Upgrading an earlier per-user installation keeps that user's app data and saved skills. CI targets both operating systems and performs packaged-app/profile smoke tests plus an isolated Windows install/upgrade/uninstall check. `npm run desktop:smoke` runs the source-shell check locally. The regular Vite app, portable npm package, and `npm run start` remain browser-based. See [`docs/kernel-client.md`](docs/kernel-client.md) for starting and attaching clients, reconnect behavior, and explicit kernel shutdown.

Each **Browser** tab owns one persistent, sandboxed Electron page with compact Codex-like chrome, keyboard-accessible common-address suggestions, bare-host HTTPS normalization, and optional user-directed text annotations. Browser cookies and site storage stay in a local Electron profile and are never forwarded to Pseudoharness task state, AgentMem, or model prompts. The **Git** peer is a local interface for branches, worktrees, commit history, and GitHub repository/PR/issue metadata. Its in-page **Sign in with GitHub** flow uses GitHub CLI's web/device authorization; the user completes authorization in GitHub, and the app never asks for or stores a password or token. The CLI credential store is separate from browser cookies. The app does not push branches or modify GitHub items. New Luna workers can use a bounded workspace tool to open these views and inspect a minimal GitHub status summary, but cannot read browser page contents, obtain cookies, or perform GitHub writes. See [`docs/browser-github-and-parallel-workers.md`](docs/browser-github-and-parallel-workers.md) for data locality, annotations, authentication, and limits.

Each session's compact Heads-up panel keeps its status, route, cumulative session tokens, and settings attached to that workspace; its expandable rows hold current sessions and saved/current project details. Each current-session row opens that exact Codex thread through a validated desktop link.

The app uses your installed Codex runtime; it does not ask for or store an API key. First-run settings have an empty workspace and AgentMem project, so no author-specific path or knowledge-base identity is required. If `codex` is not on `PATH`, set `CODEX_EXECUTABLE` to the CLI executable path before starting. `CODEX_HOME` can select a non-default Codex configuration directory.

The code uses Node's cross-platform process and path APIs. Electron packaging targets macOS (x64/arm64 ZIP) and Windows (x64 NSIS), and GitHub Actions is configured to build and test both. This implementation pass was run on Windows; macOS execution was not available locally, so confirm the current macOS CI run before treating that platform as verified. Linux is intended but not independently verified. Codex CLI availability, model access, and sign-in are external prerequisites on each machine.

## Request routing

The router receives the current request and bounded conversation context, then returns a route, rule ID, and brief reason. Its Fast capability is checked before classification; the app does not substitute another speed or model. Direct and simple requests do not start the configured hard-task orchestrator. That Codex model and effort apply only after a request is routed to a hard task; recruited execution roles use the separately selected DeepSeek Harness provider, model, and requested native effort. The task details panel records the selected route and executor.

Codex-backed roles run in the versioned, app-owned `agent-codex-home-v2`, a compatibility overlay rather than the user's normal session home. At each app launch it refreshes hard links to the normal Codex config and selected profile config, plus a link to the configured plugin directory; it intentionally omits the global Codex-home `AGENTS.md` and does not copy session histories or link the global `auth.json`. Authentication uses the app-server's short-lived token bridge into app-owned runtime state. Codex roles use the selected repository as their working directory. Codex execution roles retain repository instruction discovery, available configured MCP servers, plugins and Codex apps, subject to their role policy, task scope, sandbox and native approval behavior. Pseudoharness marks only the explicitly selected project root trusted in the thread config so Codex discovers that repository's `AGENTS.md`; sandbox and approval settings remain independently enforced. Recruited DeepSeek Harness roles instead run as task-owned SDK sessions with an isolated profile, explicit MCP gateways, validated worktree, and a fixed permission grant for each phase. The router remains classification-only with MCP, plugins, apps, web search and project instructions disabled. All roles receive Pseudoharness-owned role instructions; resumed Codex threads receive them again. Pseudoharness verifies the normal Codex MCP/plugin configuration before starting a thread and checks reported instruction sources, rejecting global Codex-home or out-of-workspace instructions. The app continues to suppress automatic skills and user memories, native multi-agent delegation, hooks, and ambient environment/collaboration instructions. It supplies its own compaction prompt. Old thread records remain visible, but threads created under an older role configuration cannot resume; send a follow-up to start a fresh pass.

Codex still provides its mandatory system, platform, security, tool instructions and schemas. Codex native tools follow the existing sandbox, project write roots, approvals, and network policy; exposing a configured tool does not authorize an unrelated side effect. With a registered AgentMem project selected, direct-answer and simple-implementation turns get fresh query-scoped knowledge before Luna answers or acts. Codex execution roles can independently use project-scoped AgentMem KB and repository-index tools. Recruited DeepSeek Harness roles receive only the task-scoped AgentMem and saved-skills gateways in their isolated profile. Both gateways pin the selected project and exact registered repository, remove caller-controlled identity fields, and withhold project/repository registration and unrelated lease-management tools. Pseudoharness records model-issued tool events separately from app-prefetched context and validates required reads and post-change index refresh before accepting artifact-producing work. No-change cases must state why in the receipt. Other user-configured MCP servers retain native Codex discovery and approval behavior for Codex roles; they are not copied into a DeepSeek Harness profile. A selected project's identity or retrieval failure stops project-context work with an actionable error. With AgentMem disabled, general answers can proceed without claiming project knowledge, while explicit project-knowledge requests ask for an actionable project selection. The router remains classification-only. Recruited workers start with a read-only context-planning stage, receive app-mediated context in a separate composition stage, and then receive the validated assignment for execution. The first two phases have no write scope; the execution phase receives either the read-only preset or, only under explicitly selected Full access, the native unrestricted grant. If selected-project retrieval fails, execution stops and the app reports the unavailable context, releasing its work lease when possible. Configured Codex filesystem skills are searchable only after a user types `/skill codex:`; the explicit selection is resolved by a stable path hash and bounded before use. Legacy assignment `skill_refs` do not trigger automatic loading. Codex's public app-server protocol, the installed DeepSeek Harness SDK, and Pseudoharness role controls define the capabilities; Pseudoharness does not claim to reproduce the proprietary desktop UI.

**Saved application skills** live in a passive, app-wide SQLite library at `skills.sqlite3` in Pseudoharness app data (schema version 2), shared across projects within the current OS user profile. Its database and supporting files stay in that profile's app-data directory; skills are not synced through AgentMem or a shared service. Opening the app or Skills tab does not read or load skill bodies. Users can create or import a `SKILL.md` package, search, preview, edit, and archive it; imports are copies with bounded safe support files and never run scripts. Type `/` in the composer to open the local skill picker; continue typing to filter by name or description, then select a result to insert a revision-pinned reference such as `/skill library:<id>@<sha256>`. This keeps the chosen revision stable if the library is edited before the pass is sent. Installed filesystem skills remain available through `/skill codex:`. The exact selected revision and source are saved in that pass. Execution roles can also explicitly call `skills_list`, `skills_search`, `skills_load`, `skills_read_file`, and `skills_save` MCP tools; only explicit `skills_load` reads the full body, and saves require the current revision to update. The router does not receive these tools. Existing filesystem `skill_refs` no longer cause automatic loading, and the library namespace `library:<id>` keeps stored skills distinct from installed Codex skills.

## Install the portable package

Build a local tarball with the compiled app and its bundled runtime dependencies:

```sh
npm ci --include=dev
npm run package
```

The output is `artifacts/pseudoharness-1.1.1.tgz`. Copy that file to another machine with Node.js/npm and Codex CLI, then install and start it:

```sh
npm install --global ./pseudoharness-1.1.1.tgz
pseudoharness
```

Open <http://127.0.0.1:4174>. The app binds to loopback only. Stop it with Ctrl+C; remove it with `npm uninstall --global pseudoharness`. If your npm global prefix is not writable, use a user-owned prefix or install from the source checkout below. The package contains compiled app files, the owned delegation policy, MIT license, and the three server runtime dependencies. It excludes source history, tests, local settings, sessions, build caches, temporary files, and AgentMem data. It does not include Node.js or Codex CLI.

## Run from source

```sh
npm ci --include=dev
npm run dev
```

Open <http://127.0.0.1:5173>. Vite proxies API and event-stream requests to the local backend on port 4174. Press Ctrl+C to stop both processes. To run the production server directly from the checkout, use:

```sh
npm run build
npm start
```

Open <http://127.0.0.1:4174>. `npm run package` rebuilds from clean output directories before creating the tarball. `PORT` changes the backend loopback port. `PSEUDOHARNESS_DATA_DIR` selects an alternate absolute path for local state.

By default, settings and task history stay in the OS user-data directory: `%LOCALAPPDATA%\\Pseudoharness` on Windows, `~/Library/Application Support/Pseudoharness` on macOS, or `$XDG_DATA_HOME/pseudoharness` (default `~/.local/share/pseudoharness`) on Linux. These paths are outside the install/package directory.

## Configure and use

On first launch, Settings asks for the exact workspace root. Select **Browse** beside the read-only path field to open the folder chooser. Expand folders in place to inspect subdirectories, select a folder row, then choose **Use this folder**; the tree loads children only when expanded, and larger lists reveal more rows in batches. Choose **New folder** to create a single folder inside the selected location; the chooser selects it, but you still need to choose **Use this folder** and save Settings to apply it. Cancelling after creation leaves that new folder on disk. You can also enter a path in the chooser and choose **Go**. Selection only fills the unsaved setting until you save. The browser shows the current OS user's accessible folders and drives (on Windows) and does not bypass filesystem permissions. Settings lists actual registered AgentMem knowledge bases whose memory directories are under the configured `projects` directory. Choosing one pairs it with its registered workspace root; **Disabled** keeps the current workspace and skips AgentMem for new tasks. Save applies the pair, while Cancel discards it. The app does not register, adopt, or rebind directories. If the AgentMem service is unavailable, the picker explains the error and offers a retry. Existing tasks retain their original workspace and AgentMem project.

The composer has selectors for the Codex hard-task orchestrator model and its catalog-supported effort, the DeepSeek Harness provider/model and requested native effort, and the approval policy. These choices are saved for new passes. The router and direct/simple Codex roles keep their fixed model and effort. A catalog entry does not establish model entitlement, so a task can still be blocked by the signed-in provider. DeepSeek Harness reports the requested native effort but not the effective effort. The selected orchestrator decides whether policy permits a direct answer or requires a complete delegated assignment; the app does not use a prompt-length shortcut.

Each expanded **Run receipt** contains a collapsed **Current workspace changes** disclosure. Open it to view read-only file cards with actual added/deleted line counts and per-file **View changes** disclosures; the adjacent Refresh button does not toggle the section. Small untracked text files are included. Git data is fetched only when the section first opens (or Refresh is pressed); it compares the task's current workspace with `HEAD`, not a pass-start snapshot, and never stages or reverts files. The worker-reported change list remains separate from this live Git view. Repositories outside the selected workspace and files outside that repository are not shown.

Provider-exposed assistant commentary, readable reasoning summaries, and tool activity appear incrementally in the relevant direct-answer, simple, orchestrator, or recruited worker transcript. Tool rows show their running/completed/failed state and disclose command details or output on demand; worker activity remains grouped in a collapsed panel, and the final output remains distinct. Activity is scoped to a role and turn, reconciled against completed item snapshots, and persisted with the pass so it remains visible after reconnect or reload. Pseudoharness requests readable summaries only: it does not request, capture, persist, or display raw hidden reasoning. Providers may omit commentary or summaries. See the [Codex app-server protocol](https://github.com/openai/codex/tree/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/app-server-protocol) and [configuration reference](https://developers.openai.com/codex/config-reference/).

At the end of each pass, the usage footer shows available token and cost data plus approximate changes in the account's 5-hour and weekly Codex allowance snapshots. Codex thread queries provide Codex estimates; DeepSeek Harness usage and effective effort are not currently reported as Codex account usage. Allowance percentages are differences between account-wide `account/rateLimits/read` snapshots around Codex role turns, with sample times and window reset boundaries saved per pass. Concurrent Codex clients or delayed/coarse snapshots can affect them; unavailable or reset-crossing windows stay unavailable. These pass snapshots are not recalculated when settings or later account state change. Missing token or credit data stays marked unavailable; older saved passes do not gain fabricated zero counts. Usage events update local state without scheduling another model turn.

Assistant responses, receipts, and readable summary text use safe Markdown rendering with GitHub-flavored tables and lists. The composer is a single Markdown source editor: inline formatting renders as the caret moves away and the original markers reappear when editing that segment. It sends the exact source text; there is no separate preview mode. Raw HTML is not enabled, and unsafe link protocols are not activated.

Codex approval presets map to app-server values: **On request** uses `on-request`, **Untrusted commands** uses `untrusted`, and **Never ask** uses `never`. **Full access (auto approve)** uses `approvalPolicy: never` and `danger-full-access` for Codex turns. The selected policy is saved on each pass, so changing Settings affects new passes without changing historical ones. Recruited DeepSeek Harness phases use read-only access for assignments without writes. A writable DSH assignment runs only when Full access was explicitly selected; then the native process is unrestricted and assigned paths are task instructions, not OS confinement. DSH cannot answer approval requests or change permissions inside an active SDK session, so unsupported writable modes fail closed. The app presents supported Codex approval requests with the requested command or permission details and sends an explicit accept, decline, or cancel response.

## Workflow and boundaries

- The app validates and stores the complete assignment before starting a worker. Recruited workers first receive a read-only context plan, then compose relevant context from the app-mediated AgentMem result, then execute the validated assignment. The first two phases have no write scope; the execution phase stays read-only for a no-write assignment and uses unrestricted access only for an explicitly authorized Full access assignment. Empty read scope is valid for an answer-only task; it grants no additional access. Non-empty write scope must be absolute and inside the configured project worktree.
- Each new user prompt after a pass ends gets its own assignment and receipt history plus fresh Codex threads and task-owned DSH sessions. Corrections and updates received while a pass is active stay attached to that pass. The next orchestrator turn receives bounded, role-labeled user-visible history, including prior direct answers and accepted orchestrator responses, so follow-ups such as “double that result” retain meaning. Past requests remain context rather than current instructions. Assignments, receipts, worker transcripts, tool output, and internal reasoning are excluded.
- Each session has its own Heads-up panel with status, routing, current Codex and DeepSeek Harness sessions, cumulative available token totals, and session/current project settings. It remains attached to its owning tab; it is not a transcript viewer. A workspace file or knowledge-base statement is not evidence that a document is public; the models are instructed to verify that it is tracked and present in the relevant remote repository before making that claim.
- Each recruited DSH role uses a separate SDK session for each fixed-permission phase. Context planning and composition use the read-only preset. A writable execution phase starts a separate process only after the selected policy and assignment allow that grant; no process is elevated in place. A directly related correction starts from the saved pass state, while unrelated tasks get fresh sessions.
- Worker outcomes are validated before review. The `type` discriminator selects receipt versus escalation; nullable fields for the other branch are ignored for receipts, while incomplete escalations report the missing decision, evidence, or options without echoing model output.
- Only explicit user input, a structured worker escalation, or the final receipt schedules the orchestrator. Progress and tool events update the UI only. Worker transcripts are not forwarded to the orchestrator.
- Task and thread state is persisted under the operating system's local application-data directory. A restart pauses active work for explicit inspection; the app does not silently replay a turn. Cancellation is persisted before interrupting and ignores late events.
- Codex simple-work turns retain their existing Codex sandbox and approval behavior. DeepSeek Harness phases use the native read-only preset when the assignment has no write scope. Writable DSH phases require explicitly selected Full access, which is unrestricted; assigned paths remain task instructions rather than an OS-level boundary. Cancellation and kernel shutdown terminate owned provider process trees. The installed DSH SDK does not report effective reasoning effort and does not support in-session approval responses, steering, or graceful per-session cancellation.
- AgentMem is accessed through the configured MCP stdio service after verifying project ID and root. Settings may leave it disabled, select an existing project, or enable per-folder KB setup. In the latter mode the execution agent receives an audited model-visible registration tool; the app derives a collision-resistant ID from the selected folder and reuses an existing registration for that exact root. The app supplies the authoritative root and ID, rejects conflicting bindings, and keeps router and read-only direct-answer roles from initializing a KB. Registration is only empty scaffolding: the agent must index safe source files, attach or inspect cited evidence, and record only verified task facts. The app retrieves scoped context before assignment and records work receipts separately from runtime thread state. Before completion, it follows AgentMem task-context continuation offsets until all mandatory current requirements and task acceptance criteria are included. An accepted app receipt asks AgentMem to complete its work task with evidence-backed checks and releases the lease only when accepted. Incomplete work stays open and releases ownership; blocked work is marked blocked then released; cancellation releases ownership. A disconnected stdio transport is invalidated and recreated on the next request. Reads and idempotent receipt/release calls retry once; receipt writes reuse the task-scoped idempotency key and exact payload, receipt failures stay visible; when lease release cannot be confirmed, the app retains that lease and offers retry using it.
- This is a single-user local app without login. The service checks loopback host/origin, uses an in-memory token for mutations, bounds request sizes, and launches subprocesses without interpolated shell commands. Do not expose its ports to a network.

## AgentMem MCP configuration

Pseudoharness reads `config.toml` with a TOML parser and validates the configured AgentMem stdio `command`, optional string-array `args`, and string-valued `[mcp_servers.agentmem.env]` entries. Multiline TOML arrays, quoted values, and ordinary nested tables are supported. Malformed TOML and invalid field types stop configuration with a field-specific error. The configured environment map is forwarded to the direct AgentMem client and through the scoped model gateway; matching values in the Pseudoharness process environment override values from the TOML file. The map is carried in process configuration and is not written to logs.
